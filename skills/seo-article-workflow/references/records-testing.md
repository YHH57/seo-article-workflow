# 状态、版本与测试记录

## 记录与实际任务相称

普通小修保留旧稿、当前稿和简短修改记录即可。逐阶段流程测试保存足够重建决定的输入，避免在对话丢失后从头猜测。不要给每个任务创建所有模板的空副本。

测试阶段交付包括：目的；输入及来源；实际工具、URL、完整搜索词和条件；结果、失败与缺失；事实/推断/选择理由；与上一阶段的变化；产物与下一步。查询前展示方案，查询后记录假设决定。

建议用 run.json 作当前索引，关联按需生成的业务简报、情境/问题/候选、查询记录、证据包、作者配置、大纲、链接计划和正文。路径是任务相对路径，不把本机绝对路径写进可分发 Skill。

每个 artifact 记录 path、sha256 与角色。当前正文和审阅报告绑定同一内容版本；如果保留多种大纲格式，由一个事实来源生成或同步核对。

## 状态

- 查询状态与指标状态按 research.md 分开。
- 稿件可为 working、awaiting_user_review、approved 或 delivered。只有真实用户接受才标 approved；完成技术检查不代替接受。
- 单次交付完成不等于整体流程已验证；发布、索引、排名独立于稿件状态。

`article` 可为空，表示本轮尚未写正文。不要为了让模板字段完整而提前生成下游产物。平台、市场、语言变体、费用、模型标识等未确定信息保留 null。

## 首次输出与复现边界

测试写作规则时，保存实际采用的完整任务级提示词、原始输入或其不可变快照、作者配置版本和首次完整输出。语言修改另存版本并解释原因，不把修过的稿冒称首次输出。

记录哪些更早稿件已在上下文中、哪些输入改变；不把当前对话说成盲测。平台系统指令、不可见推理或未捕获的模型参数不假造为已记录。脚本只是文件生成/转换时，不声称是独立写作模型。

## 通用性与收尾

测试记录将问题分为：本篇内容、执行不到位、候选规则缺漏、编辑偏好。修某篇的模具分工、咖啡研磨举例或软件功能对照，都不意味着其他主题必须采用对应结构。

建议写回 Skill 时说明原规则位置、观察证据、最小改动和下一次测试输入。新主题、不同文章类型或不同发布模式的行为检查比重复改一段结尾更能发现过拟合；测试时不给评估者目标答案。

结束一轮前固定当前稿、已决定项、剩余实质问题与可选增强。优先修已确认问题并交付，不在每轮审阅后自动扩展修改范围。

## 文件核对器

`scripts/validate_run.py` 仅只读检查：artifact 是否存在且哈希相符、稿件接受状态是否一致、指标空值、复用请求条件、来源读取范围与全文声明、计划 URL 出现次数。它接受一个任务目录内的 run.json，可按模板建立记录。

查询 JSON 是 query-record 模板对象的数组；证据 JSON 包含 sources/claims 数组。链接计划可在 run.json 的 link_plan 数组里配置 url、role、occurrences。设置数量来自单篇计划，脚本不内置品牌上限、引用数量或字数。

检查器不联网、不安装依赖、不修改文件，不验证用户同意的真实性或来源本身的事实。输出应与人工审阅一起解释。
